AWS GPU Testing Recommendation and Setup Note

Purpose

This note preserves the recommended cloud GPU testing path in case the project selects Amazon Web Services for the next external validation run.

Current interpretation

Hugo's GPU failure cannot be root-caused without the actual error message, but the local CPU smoke path remains runnable. The most likely failure classes are environment or invocation issues rather than a complete training-path failure:

- wrong Python interpreter or wrong PyTorch build
- CPU-only PyTorch selected on a GPU host
- CUDA-visible GPU not available to PyTorch
- running the setup script from the wrong working directory
- missing zsh on the target machine
- GPU memory pressure from the default non-smoke GPU configuration

Immediate diagnostic command for any GPU host

Run this before starting training:

```bash
python - <<'PY'
import sys
import torch

print("python:", sys.executable)
print("torch:", torch.__version__)
print("cuda build:", torch.version.cuda)
print("cuda available:", torch.cuda.is_available())
if torch.cuda.is_available():
    print("gpu:", torch.cuda.get_device_name(0))
PY
```

Recommended AWS path

Use an official AWS Deep Learning AMI for PyTorch with NVIDIA drivers and CUDA already configured. This avoids spending time debugging a hand-built CUDA stack.

Preferred pattern:

1. Launch a single-GPU EC2 instance using an AWS Deep Learning AMI for PyTorch.
2. Start with an L4/A10-class GPU instance for smoke and moderate subset testing.
3. Use the AMI's bundled PyTorch Python path explicitly through `PYTHON_BIN`.
4. Run a small smoke test first.
5. Increase dataset size and batch size only after the smoke run passes.

The AWS Deep Learning AMI documentation gives the current PyTorch GPU AMI naming and activation details. At the time this note was written, AWS documented PyTorch GPU DLAMIs that support G4dn, G5, G6, P4, P5, and related NVIDIA GPU instance families.

AWS setup sketch

```bash
git clone <repo-url>
cd ves

# Use the Python that ships with the Deep Learning AMI.
# Install non-Torch runtime packages only so the DLAMI GPU PyTorch build is preserved.
/opt/pytorch/bin/python -m pip install -r requirements-dlami.txt

/opt/pytorch/bin/python - <<'PY'
import sys
import torch

print("python:", sys.executable)
print("torch:", torch.__version__)
print("cuda build:", torch.version.cuda)
print("cuda available:", torch.cuda.is_available())
if torch.cuda.is_available():
    print("gpu:", torch.cuda.get_device_name(0))
PY
```

First smoke run

```bash
cd model

PYTHON_BIN=/opt/pytorch/bin/python \
VES_SMOKE_TEST=1 \
VES_MAX_SIZE=64 \
VES_BATCH_SIZE=2 \
VES_NUM_EPOCHS=1 \
VES_SIZE_PROFILE=64 \
VES_SEED=42 \
./setup.zsh
```

Moderate validation run after smoke success

```bash
cd model

PYTHON_BIN=/opt/pytorch/bin/python \
VES_SMOKE_TEST=0 \
VES_MAX_SIZE=2048 \
VES_BATCH_SIZE=8 \
VES_NUM_EPOCHS=1 \
VES_SIZE_PROFILE=96 \
VES_SEED=42 \
./setup.zsh
```

If the moderate run fails with CUDA out-of-memory, retry with:

```bash
PYTHON_BIN=/opt/pytorch/bin/python \
VES_SMOKE_TEST=0 \
VES_MAX_SIZE=2048 \
VES_BATCH_SIZE=4 \
VES_NUM_EPOCHS=1 \
VES_SIZE_PROFILE=96 \
VES_SEED=42 \
./setup.zsh
```

The setup script writes each run under `model/runs/<timestamp>-<commit>/` by default. Set `VES_RUN_DIR=/path/to/run` if the output location needs to be fixed. Use `VES_DEBUG_CUDA=1` only while diagnosing CUDA errors because it enables launch blocking. Non-smoke runs default to no hard timeout; set `VES_HARD_TIMEOUT` explicitly if the run must be bounded.

Information to record from each AWS run

- EC2 instance type
- GPU model and VRAM
- AMI name or AMI ID
- Python executable
- PyTorch version
- CUDA build shown by PyTorch
- `torch.cuda.is_available()` result
- command used
- run directory
- seed
- dataset size
- batch size
- size profile
- runtime
- train loss
- validation loss
- whether checkpoint and final model were saved
- any error text if the run fails

Recommendation

Use AWS first for a clean, institutionally legible benchmark. AWS is not necessarily the cheapest path for iteration, but an AWS Deep Learning AMI run is easy to describe in a later Purdue, ACCESS, or other university compute request.

Once the training path is stable, cheaper providers such as Lambda Cloud or RunPod may be better for repeated iteration. Keep the AWS runbook and results as the reproducible baseline for formal compute requests.
